## 1. Purpose
The purpose of the S2-3 pipeline is to structure and prepare the final classification dataset for the downstream Random Forest model (S2-4). It isolates the predictive features ($X$) from the classification target ($y$), tests the integrity of the target labels according to authoritative Student 1 thresholds, and explicitly removes features that would cause data leakage.

No models are trained or evaluated in this stage.

---

## 2. Input Dataset
**File:** `output/feature_data.csv`

Generated by the S2-2 feature engineering pipeline. Contains 590,985 records and 10 columns.

---

## 3. Authoritative Congestion Methodology
The pipeline adheres strictly to the S1-6 MapReduce logic. The authoritative definition of congestion used across the TrafficLens project is derived per-sensor relative to historical baselines.

## 4. Congestion Score Formula
$$ \text{Congestion Score} = 1 - \left( \frac{\text{Current Speed}}{\text{Reference Speed}} \right) $$
Where Reference Speed is the historical mean for that specific sensor (computed in S1-4).

## 5. LOW/MEDIUM/HIGH Thresholds
The continuous score is bucketed into discrete classes:
- **LOW:** $\text{score} < 0.3$
- **MEDIUM:** $0.3 \leq \text{score} < 0.6$
- **HIGH:** $\text{score} \geq 0.6$

## 6. Target Definition
The classification target ($y$) is `congestion_class`. It uses the human-readable labels `LOW`, `MEDIUM`, `HIGH`. No numerical encoding is applied at this stage, leaving categorical handling up to the S2-4 model pipeline.

---

## 7. Feature Selection
The model features ($X$) selected for downstream training are:
1. `sensor_id`
2. `hour`
3. `day_of_week`
4. `is_weekend`
5. `current_speed`
6. `previous_speed`
7. `rolling_average`

## 8. Target Leakage Prevention
To prevent trivial target leakage, `congestion_score` is explicitly **excluded** from the model features ($X$). Because `congestion_class` is a direct thresholding of `congestion_score`, including it would allow a model like Random Forest to trivially split on the score thresholds without learning anything about traffic patterns (speed, time, lags). `congestion_score` is retained strictly as metadata for traceability.

## 9. Sensor ID Handling
`sensor_id` is retained as an integer identifier. While treating it as a continuous numeric feature might introduce false ordinal relationships in simple linear models, downstream tree-based algorithms (like Random Forest in S2-4) can learn non-linear splits on such identifiers. No target encoding was performed here to keep the data clean and prevent data leakage.

## 12. Data-Quality Validation
- **Row count:** 590,985 records input, 590,985 records output.
- **Unique sensors:** 207
- **Target mismatch detection:** 14 records were found where `congestion_score` (parsed from the CSV) did not mathematically align with `congestion_class`.
  - *Investigation:* All 14 records had scores of exactly `0.3000` or `0.6000` in the CSV. Because the S1-6 `awk` script formatted floats using `%.4f`, a score of `0.29996` (which is `< 0.3` and thus correctly classified as `LOW` in S1-6) was rounded and printed as `0.3000`. 
  - *Resolution:* The authoritative S1-6 labels are preserved without modification. This is a known floating-point rounding artifact, not a data corruption error.
- **Duplicates:** 0 duplicate records.

---

## 13. Boundary Validation
Programmatic threshold tests confirm that the Python boundary checking mirrors the authoritative `awk` thresholding logic:
- Score: `0.299999` $\rightarrow$ `LOW`
- Score: `0.3` $\rightarrow$ `MEDIUM`
- Score: `0.599999` $\rightarrow$ `MEDIUM`
- Score: `0.6` $\rightarrow$ `HIGH`
